# Draft interoperability schemas

The three original JSON Schema examples retain their `0.1` wire labels because the design revision number is not an automatic wire-format change. They describe action proposals, capability manifests and evidence claims; they are not production authenticated encodings.

The schemas use bounded JSON integers within the original interoperable range. The Rust reference has separate exact typed integers and is not a serializer for these schemas. The FA-005 reference profile below supplies canonical draft bytes and duplicate-field handling. Production activation, migrations and authenticated transcripts remain later contract/compiler work.

The Python schema checker from the first draft is removed. Preparation may use external standard tools to check these static documents, but no Python runtime is shipped or needed by the Rust reference. The current xtask is not a general JSON Schema validator. Full in-family format/registry compilation and conformance must precede live protocol use.

## FA-CJSON/0.1 reference byte profile

The reference encoder/decoder in `fa_reference::canonical_json` supports exactly the three existing `fa.action/0.1`, `fa.capabilities/0.1` and `fa.claim/0.1` shapes. It does not change their wire labels or act as a general JSON Schema validator. This is an implementation of the existing “Canonical evidence identities” engineering addition serving FI-A06 (plan §7.1, FA-005), not a new essay claim.

Canonical documents use UTF-8 with object keys in ascending UTF-8 byte order, no whitespace outside strings and no trailing newline. Arrays preserve their declared order; duplicates refuse only where the schema requires uniqueness. Integers use unsigned decimal digits without signs, leading zeroes, fractions or exponents, within the schema's explicit range. Text preserves Unicode scalar values without normalization; schema text lengths count characters, while identifiers remain restricted to their ASCII pattern. Strings use `\"` and `\\`, the short backspace/form-feed/newline/carriage-return/tab escapes, and lowercase `\u00xx` for the remaining U+0000–U+001F controls. Other characters, including slash and U+2028, remain literal UTF-8.

The decoder rejects duplicate keys, unknown or missing fields, wrong shapes, invalid values, out-of-range integers and noncanonical bytes. The profile deliberately narrows JSON Schema numeric spelling: integral forms such as `1.0` and `1e0` remain noncanonical here. It parses and validates, then compares the original bytes with the canonical encoding; it does not silently normalize a noncanonical document. The encoded document is an opaque validated value: callers can clone, compare and inspect its schema variant, but cannot mutate fields or construct an unchecked payload. `validate_json` accepts an already parsed syntax value and applies the same three-shape and numeric-profile validation.

The parser limits a document to 512 KiB, nesting depth 8, 1,024 syntax values and 8,192 decoded string bytes. These limits cover the schemas' maximum text lengths, including four-byte Unicode and six-byte encoded control escapes. A worst-case claim has at most 69,632 free-text characters (417,792 encoded control bytes), plus bounded ASCII identifiers, references and framing; it stays below 512 KiB. Resource limits run before field validation: an overlong four-byte string can return an input-limit refusal before a character-count error. Limits bound this reference profile, not measured allocation or process memory.

`strict_json` supplies only lexical parsing. `xtask` compiles that same reviewed syntax source through an explicit module path while retaining its independent admission decisions; no Cargo dependency edge, package, executor or runtime effect is added. Both paths belong to the reviewed source manifest. A decoded `tested_profile`, `attested_profile` or `observed_in_declared_scope` value is a declaration, not proof of its truth. Canonical bytes establish neither authentication nor authority.

Manually authored fixtures under `crates/fa-reference/tests/fixtures/canonical-json-v01/` are independent of the encoder. Their exact bytes are required; tests never strip trailing whitespace or regenerate them to pass. Runtime qualification is recorded in `IMPLEMENTATION_STATUS.md` and the retained execution receipts.
