# Checked learned publication

Learned generation can require the original final-publication witness gate in
the same immutable configuration as its model, tokenizer, fitted codec, probes,
source policy, forecasts, identity registration and helper qualification. This
composes the existing learned owner with the existing validator; it does not
introduce another validator or another source of effect authority.

## Native registration

`FileLearnedConfig::with_required_publication_validation` accepts a
`FileLearnedPublicationProfile` containing:

- `limits`: the original `PublicationLimits`, including the finite binding and
  validation-work allowances.
- `feed`: optionally, the original `GeneratedPublicationFeed`, containing the
  exact change-feed policy, producer freshness policy and explicit snapshot
  fallback selection.

The existing learned configuration already binds the stream, and the owning
constructor independently selects its recovery reserve. The new profile supplies
no evidence capture, producer heartbeat, helper verdict, human approval or
publication key. `required_publication_validation` returns this registration,
not a live evidence-health assertion.

The disjoint `FALPUB` recipe wrapper retains the complete original configuration
and encodes the selected original witness bootstrap events. Unselected recipes
retain their original bytes. A repeated selection refuses, and the complete
wrapper order remains part of the independently retained recipe identity.

The original learned Enable transition installs the witness, change-feed,
freshness and optional exact-snapshot guards before exposing a numerical owner.
It runs the original validators, including the producer clock-domain check.
Invalid or conflicting registrations refuse before a newly created store can
become visible. The same installation is used by ordinary, raw-predictive,
owned-predictive and topology-mediated learned constructors; identity and joint
credibility remain separate prerequisites.

## What must happen before publication

Each actual attempt must bind its original action and original publication
evidence before helper review. Structured witnesses can depend on exact values,
absent keys, empty ranges and complete range membership. An opaque witness binds
its complete declared input and interpretation epochs. The original producer,
capture and feed APIs retain their existing provenance and completeness rules.

Current evidence is acquired and validated at the original authorization,
dispatch and first-publication boundaries. A changed relevant value, a new
member of a previously empty range, changed opaque input, incomplete change
history or unavailable required evidence cannot be repaired by reusing a human
approval. An unrelated change remains eligible only after the original validator
establishes that the required dependencies still hold.

If a relevant change arrives after dispatch admission, the first-publication
gate uses its original sealing operation. It does not deliver the obsolete
effect, reinterpret the old review, or treat cancellation as proof of a remote
outcome. The original dispatch charge, settlement rules, historical review and
request identity remain authoritative.

## Recovery and historical inspection

Every learned recovery, historical receipt and audit path already compares the
complete independently supplied numerical recipe against the canonical journal.
The new registration therefore participates in those same comparisons. Omitting
or changing its limits, feed, freshness or fallback policy cannot reopen the
same history under a weaker recipe. Mismatch refusal precedes numerical replay,
staging cleanup, the recovery fence and role release.

A matching recovery still pauses the original numerical owner and withdraws
old eligibility through the original fence. It preserves acknowledged tokens,
sampler draws, forecast expenditure, effect liabilities and original receipts.
Fresh evidence and both original effect keys remain necessary for a new
publication. Historical inspection cannot manufacture a new capture or turn an
old receipt into permission to send again.

## Runnable learned operator

The existing learned publication commands accept a closed outer object with
exactly these fields:

| Field | Value |
|---|---|
| `schema` | `"fa.learned-checked-publication/1"` |
| `publication` | Absolute path to an original supervised witness profile |
| `recipe` | The complete original learned recipe object, optionally inside the existing identity and joint envelopes |

Canonical composition is `checked(identity(joint(original)))`; either identity
or joint, or both, may be omitted. The original recipe can be any version from
`fa.learned-publication/1` through `/6`. Repeated or reversed wrappers, unknown
fields and unsupported versions refuse. Unwrapped recipes retain their existing
behavior and exact native configuration bytes.

The optional [credential envelope](LEARNED_CREDENTIAL_PUBLICATION.md) surrounds
this complete object. Its original live capability composes with every supported
witness profile, including finite waiting, while retaining both review keys and
the independently selected credential recovery contract.

For example, save that outer object as `/operator/checked-recipe.json`, retaining
the complete original recipe under its `recipe` field, and use the existing
commands:

```sh
supervise_publication create-learned-generated CONFIG /operator/checked-recipe.json REVIEWER_PROFILE
supervise_publication create-learned-generated CONFIG /operator/checked-recipe.json REVIEWER_PROFILE --actor-profile ACTOR_PROFILE
supervise_publication create-learned-generated CONFIG /operator/checked-recipe.json --resume
```

The existing continuation, separately reviewed Finish, resident sequence,
anchored audit, receipt and terminal commands use the same selection. Their
original argument, custody and predecessor requirements remain mandatory.

### Supported witness profiles

| Original profile | Source and history contract |
|---|---|
| `fa.supervised-witnesses/1` | Original and current action-bound captures, without a change feed |
| `fa.supervised-witnesses/2` | Captures plus the original change-feed and freshness contract |
| `fa.supervised-witnesses/3` | Coupled producer image containing its capture and change feed |
| `fa.supervised-witnesses/4` | Independent cut-bound captures and feed with explicit finite producer catch-up |
| `fa.supervised-witnesses/5` | Coupled producer with explicit exact-current-snapshot fallback |
| `fa.supervised-whole-input/1` | Complete opaque producer input with strict change history |
| `fa.supervised-whole-input/2` | Complete opaque producer input with explicit exact-current-snapshot fallback |

A witness profile's separate joint-publication wrapper refuses; use the existing
learned joint envelope so its exact qualification policy stays part of the
learned recipe. That requirement is never silently dropped.

The outer recipe retains the original 64 KiB limit and adds one bounded nesting
level. Reading the witness profile consumes the original aggregate learned asset
allowance. Its schema, producer scope, clock domain and supported mode are checked
before model loading or durable startup. This admission opens no live capture,
producer or feed file.

### One evidence binding per actual request

After the original gateway admits a Message or Finish, the operator obtains that
attempt's actual frozen action and binds its original publication evidence before
launching native or process helpers. The retained preparation object contains
readers, not a cached current observation or approval. Each native/process review
step and the original computed authorization, dispatch and publication driver
use the existing source-acquisition wrappers around the original learned-input
provider. A witness file cannot replace a native helper input.

A coupled producer supplies capture and feed from one original image; independent
sources retain their explicitly sequential acquisition contract. Required source
eligibility is withdrawn before acquisition. Missing files, stale producer time,
incomplete history or a relevant change reach the original refusal/sealing path.
Successful rereading does not renew the producer's timestamp.

Feed catch-up reads its original bootstrap cut from either the standalone native
registration or the already independently bound learned Enable configuration.
The same lookup serves atomic feed completion. It does not reconstruct runtime
configuration from saved bytes or change the existing source, conflicting-history
or missing-prefix checks.

Completed cooperative generation returns its acknowledged historical replay
custody to the same live owner. The prompt-to-forecast handoff preserves that
custody as well, and terminal forecast completion retains its original result.
Publication acquisition then replays the unverified suffix through the existing
control cache while still reopening current evidence at every required boundary.
This prevents repeated full numerical-history replay from consuming a resident
workflow's deadline. The exact custody and batch rules are documented in
[learned publication replay](LEARNED_PUBLICATION_REPLAY.md).

The plain-capture preparation path now distinguishes an explicitly absent feed
from a feed whose state is missing or mismatched. It no longer requests a
snapshot-fallback status that cannot exist for a valid no-feed owner. Exact
limits still match first, a selected feed remains mandatory, and a plain profile
cannot operate a feed-backed owner by omitting its selection.

### Finite producer catch-up

Select `fa.supervised-witnesses/4` with the original independent `original`,
`current` and `feed` fields, plus `max_retries` in `1..=64`. The original capture
must contain its explicit producer input cut. The schema retains the original
structured-witness requirement; it cannot convert a legacy capture or a missing
feed prefix into eligible evidence. Other schemas retain strict acquisition.

A producer snapshot may lag invalidations in a complete feed. When its identity,
generation, contents, included cut and structured floors still satisfy the
original deferral contract, each real read can record a Deferred observation.
That observation installs no current witness and grants no publication right.
Missing history, malformed bytes, equivocation, rollback and independent policy
or helper-input failures retain their original refusal behavior.

Native and process review can continue with their actual learned inputs during
this lag. Their existing inference, process, poll and phase budgets still apply.
These review acquisitions do not spend the final-publication retry allowance.
After the original review and human approval, only the native ready-job waiting
diagnostic can yield to another acquisition. The same prepared request, frozen
action, review, approval and any existing reservation survive that yield. The
next iteration checks the unchanged logical/wall deadline, authenticated Stop
and actor cancellation before reading again.

`max_retries` bounds extra waiting decisions for that actual prepared request;
persistent lag therefore permits at most `max_retries + 1` deferred final steps
before the existing failure/Stop/drain path. A frozen clock cannot reset the
counter. Each separately admitted resident Message or Finish gets its own finite
budget, while the existing cumulative numerical and effect accounting remain
unchanged. No delay extends a human approval, source lease or action deadline.

Waiting is orchestration state, not an additional native grant: `/2` and `/4`
with identical validation/feed/freshness fields retain identical native policy
registration. Historical inspection still binds that policy and needs no live
capture, feed or helper. Recovery fences old jobs and keys instead of replenishing
an old waiting request. Once dispatch has occurred, acquisition follows the
original strict first-publication and receipt path, with no new wait window and
no refund of an unknown outcome. See [supervised capture
deferral](SUPERVISED_CAPTURE_DEFERRAL.md).

### Resident and historical ownership

Resident entries must retain one exact native publication policy. Per-attempt
source paths and witness requests may differ, but each actual request binds its
own original evidence. A later failed attempt cannot erase an earlier confirmed
message, reset forecast or numerical expenditure, reuse either effect key, or
turn Finish into an unreviewed operation.

If an original binding failure quarantines the owner, final reply grace still
drives the same authenticated, observation-only actor transport. It can deliver
the original `ControllerUnavailable` knowledge without consulting a live ledger
that has become unavailable. That response preserves uncertainty; it is not a
successful Stop or a nonexecution receipt. The original quarantine, failed
drain result, request restrictions and reply budgets remain in force.

Historical operations require the independently selected profile file so they
can reconstruct the exact recipe. They do not require current capture, producer,
feed, native-helper roster or identity-observation files. The original model,
tokenizer, fit and other historical replay inputs remain required. An absent or
changed selected policy fails before staging cleanup or a recovery write.

## Scope

This is a bounded reference integration of FA-062, plan sections 7.6–7.7, 8.7–8.8
and 16.4, and the existing Epistemic MVCC judgment-witness addition serving
FI-A13/FI-A17. It changes no plan meaning, journal tag, authority role, dependency,
revocation rule or license.

The local publication sink and operator-selected evidence sources retain their
existing trust assumptions. This is not authentication of arbitrary filesystem
content, remote delivery, a complete deployment perimeter, calibrated detection
quality or a release qualification. Current execution evidence and remaining
qualification limits are recorded in [implementation status](../IMPLEMENTATION_STATUS.md).
