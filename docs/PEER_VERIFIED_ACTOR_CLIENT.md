# Verify a local server before sending durable actor requests

`FileClientProfile::with_peer_policy` selects a Linux-only `FilePeerClientProfile` before creating a client. It binds the independently provisioned opaque server/transport identity and the original `PeerPolicy` UID, effective GID and optional PID together in the existing client recovery binding. `FilePeerClient` creates, opens and inspects the original `FileActorClient` store. Recovery requires those exact inputs, original limits, image capacity, canonical directory and independent revision floor before staging cleanup. No new storage format, authority, parser or outcome ledger is introduced. Existing raw-client profiles remain unchanged and do not acquire this guarantee.

`FilePeerClient::connect` calls the original safe `PeerPolicy::verify` on the supplied connected Unix socket before setting nonblocking mode or moving the original client. It never accepts caller-asserted credentials, a claimed server name in a reply, or a policy learned from the candidate. Any refusal closes the candidate and returns the still-locked original client with its requests, budget and revision intact; it performs no protocol reads/writes and no journal transaction. The application may explicitly retry with a corrected socket. It does not look up a path, connect automatically or create a retry loop.

The resulting `FilePeerConnection` forwards Submit, Poll, Cancel, exact retries, individual steps and bounded drives to the original write-ahead client. It exposes no raw stream or unchecked connection method. Disconnect retains the same fixed policy, and every new connection verifies again. Neither verified credentials nor old responses restore transport-local tickets: an explicit exact Submit still reacquires visibility. An unavailable durable owner cannot escape through disconnect, and a verified peer cannot bypass intent-before-I/O or acknowledgment-before-response.

This narrows a concrete source of accidental or unauthorized disclosure of original request bytes, but it is not executable attestation or remote authentication. Linux credentials describe the connection at its creation, not each subsequent holder of a transferred descriptor. UID/GID-only rules admit all processes with those credentials; pinning PID restricts that set but does not identify an executable image and can intentionally prevent reconnection after a server-process restart. The opaque application binding still must be provisioned independently and associated with the expected server. Operator-controlled file integrity, independent rollback bounds, descriptor custody and isolation remain assumptions. There is no automatic policy widening after a refused reconnect.

Five new unit regression functions cover an independently assembled binding vector, each changed UID/GID/PID with zero protocol output, successful matching controls, nonsocket refusal and corrected reuse of the same owner, fresh verification after disconnect, changed-policy/transport/floor checks before cleanup, and original intent-write failure with successful recovery. Two integration functions use real Unix sockets and the original full-input congress, separate human approval, publication and reconciliation path. They check an executed request recovered under its original key, plus message publication and separately approved finish with outcome-unknown status until reconciliation. Fixture credentials come from actual local sockets for testing only; production configuration must not use trust-on-first-use. A compile-fail doctest rejects raw-client unwrapping.

All seven tests and the doctest are source additions, not passing executions. RCH is absent in this editing runtime, so compilation, rustfmt, Clippy and Rust test execution remain unverified. No existing assertions, dependencies, server journals, wire commands, Beads states or qualification gates change.
