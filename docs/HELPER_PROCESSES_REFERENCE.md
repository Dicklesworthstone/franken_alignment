# Executable helper launch and owned child lifetimes

Consumer: the supervising host and SupervisedDriver that previously had to preconnect every HelperPool transport. This is a reference integration of FA-018/FA-019, plan sections 9.1-9.3 and 17.1, serving FI-A03/FI-A06/FI-A13/FI-A14/FI-A16. It does not complete the credential perimeter or native runtime admission.

## Executable path

`helper_processes::launch_helpers` accepts the existing CommitteeContract and an exact member-to-HelperProgram map. Every program has an absolute executable path, an absolute working directory, bounded arguments and an explicit environment map. Complete roster equality, aggregate text capacity and all path metadata are checked before the first process starts. A later socket/spawn error returns every already started child with termination requested. No reduced-roster success is returned and no helper input bytes are sent during setup.

The implementation invokes Command directly, without inserting a shell or searching PATH. It clears the inherited environment and reinstalls only the explicitly configured entries. Configuration is trusted host data, never an actor-supplied execution request. Explicitly selecting a shell or interpreter remains the host's decision. Program debug output omits paths, arguments and environment values. Field length is checked before scanning its contents, and both per-program and whole-roster text are bounded.

Each child receives its own unnamed, full-duplex Unix socket as standard input. Both standard output and standard error are directed to the host's private standard-error stream, not the actor wire or commitment parser. A worker uses `HelperClient::from_process_stdin(expected_profile)` to attach through safe owned-descriptor conversion; a non-socket standard input refuses. The original HelperClient and HelperPool still deliver, decode and compare the exact input profile, perform commit/reveal and feed the original congress. Process exit, including status zero, never counts as a vote.

## Cleanup is an owned obligation

`HelperChildren` retains direct child handles and their observed exit records. `reap` performs one nonblocking try_wait per retained live child; stop requests additionally issue at most one kill attempt per child on that pass. A successful kill request is not reported as a reaped process. Repeated polling can finish cleanup or expose an OS refusal, without creating a thread, hidden waiting loop or replacement process. Reaped children keep their terminal status and are not signalled again. The host must not independently reap children behind this owner.

A partial launch error owns its cleanup obligation. Callers must retain it, request shutdown and poll until all children are reaped. Drop attempts bounded termination/reaping and emits a diagnostic for remaining children; it cannot guarantee cleanup of an uninterruptible child or replace explicit host shutdown. Direct-child cleanup does not terminate or contain descendants. Scheduling of reap calls, executable/directory integrity, descriptor hygiene and private diagnostic routing remain host duties.

## Managed driver integration

`SupervisedDriver::start_process_review(ProcessReviewLaunch, snapshot)` connects configured executables to the original review path. The shared admission check preserves the original order of attempt, roster, complete input and predecessor-revision checks; those checks precede process creation. The new path does not supply a verdict, policy snapshot, default permit or replacement input. It calls the existing start_review with the launched streams and keeps the child owner independently of the active review job.

There is at most one owned live-or-retiring cohort per driver. Another review cannot start until all children of the previous cohort have been reaped. Completed process records can then be replaced by the next explicit launch, but a live child is not discarded to make room. This bounds owned direct children together with the existing roster bound; it is not a bound on child CPU, address space, descendants or diagnostic output volume.

A partial launch failure leaves its children owned by the driver. If all children spawn but a later original session or HelperPool limit check refuses, the driver requests their termination and retains them for reaping. Any input update or round ID already consumed by that failed setup remains consumed; there is no rollback, automatic retry or recycled round. ProcessReviewError reports the failure, while helper_processes and reap_helpers expose and progress the retained cleanup obligation.

Each driver step performs cleanup passes before and after the existing execution step, including its error return. During review, a child whose original protocol slot becomes Complete, Failed or Closed is stopped; other live children continue. Therefore a silent member reaching its commitment deadline is stopped without replacing its missing vote or preventing its healthy peer from revealing. Once review finishes, cancellation succeeds, or the active job otherwise ends, all remaining direct children are stopped. Stopping a child does not revoke an already accepted reveal, cancel a dispatched effect or refund resources. OS observations remain supervisor-only.

Approval still requires a subsequent execution step with the original current-input and authority checks. Retiring or successfully exiting every helper does not remove the independent human key requirement. The existing behavior of retaining one pre-dispatch permit and never resending an uncertain publication remains unchanged. The original fresh-clock callbacks are not replaced by process timestamps or process completion times.

## Endpoint interruption

Detaching the endpoint moves the original child owner into OfflineDriver along with the supervisor, job and permits. The offline owner can inspect, stop and reap its direct children, or cancel the active original attempt. Reconnecting under the existing endpoint-brand and fresh-fence checks moves the same child owner back; a failed reconnect retains it. No child is relaunched to recreate an earlier review, and the original actor request identity is unchanged.

Receipt acceptance and pending-effect reconciliation continue without living helper processes or current helper input. Cleanup can progress alongside those operations. A filesystem publication whose acknowledgment was lost remains an outstanding effect until its real endpoint evidence is accepted; process cleanup is not that evidence. The existing controller and FileEndpointRecovery key must survive. This work does not implement recovery after loss of the entire authority process.

## Limits and verification status

This is not a sandbox, immutable executable attestation, cryptographic worker identity, control-ledger persistence or production runtime integration. The host can explicitly pass an inappropriate credential, and the program still has its OS user's filesystem/network authority. Clearing an environment is not complete credential isolation; unrelated non-CLOEXEC descriptors and descendant processes require a real host containment profile. OS spawn is synchronous setup and is not claimed wall-clock bounded. The host must ensure that its diagnostic sink cannot disclose helper information to the actor or block the intended deployment. The existing commitment remains non-cryptographic.
