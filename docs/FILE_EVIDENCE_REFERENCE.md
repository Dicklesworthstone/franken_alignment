# Operator-file evidence and current-input capture

## Concrete source

`oversight::evidence_source` reads one explicitly provisioned operator file into the existing Snapshot and CommitteeInput contracts. It does not accept an actor-supplied path, fabricate helper judgments, select an automatic permit, or replace a failed read with cached evidence. This is scoped reference progress for FA-017/FA-057/FA-081 and plan 7.6, 9.3, 17.1 and 17.7. The source consumer is the existing supervised actor-to-effect driver.

The version-one JSON document has exactly `version`, `source`, `generation`, `scope`, `semantic_epoch`, `complete`, `values` and `contexts`. Source, generation, semantic epoch, scope IDs and value-map keys are canonical unsigned decimal strings. `version` is the JSON integer 1. Scope contains tenant, principal, run, branch, authority and the literal purpose `effect`. Values and per-member context payloads use lowercase hexadecimal; context-map names are exact committee identities. The existing strict parser rejects duplicate keys, excessive nesting and malformed input. Unknown fields, wrong types, noncanonical IDs, overflow and malformed hex refuse. `EvidenceSnapshot::encode` is the producer-side encoder.

A file is a complete snapshot only relative to the producer's declared domain. The `complete` flag is retained exactly, including false; successfully reading a regular JSON file does not establish that an external database, filesystem or environment was completely observed. Snapshot authenticity, producer correctness and temporal coherence remain host obligations.

## Binding and privacy

FileEvidenceSource freezes an absolute operator path, source ID, full effect Scope and byte ceiling. Each read opens the current file anew. It rejects wrong namespaces, descending source generations, descending semantic epochs, and changes to any parsed content under the same generation. Equal content with different JSON whitespace remains equal. A new generation is retained even when its complete flag is false. Old returned snapshots remain immutable historical data, not automatically current observations.

A failed read sets current eligibility to unavailable while retaining the surviving generation floor. It never returns the old successful snapshot as the result. Restoring the exact prior file may make that source readable again; consumers must separately invalidate live approvals on the intervening outage. A same-generation substitution cannot acquire a new meaning by being retried. The source-version floor survives only with this source object, not loss of the whole process.

inputs_for builds each actual helper input from the original exact action frame, its registered question, and a framed context containing source/version/scope/member identity followed by that member's supplied context bytes. It uses the original ActualHelperInput and EvidenceViewManifest validators. The private Snapshot value map and other helpers' contexts are never automatically copied. Context bytes are explicitly host observations, not fabricated source-span claims about an unseen document. All roster members must have a context, even when its payload is intentionally empty; an absent member is not silently dropped. A generation change changes the submitted context frame even when its payload bytes are identical.

reference_root is an explicitly non-cryptographic 32-byte reference label containing source, generation, tenant and authority IDs. It is not SHA-256, a signature or a content commitment. Full action scope and actual inputs remain separately bound by the existing reference sessions. Source IDs must be unique within the operator's registered domain.

## File and resource assumptions

The producer must publish immutable files with atomic replacement, not edit the open file in place. The selected file and every ancestor must be controlled by the operator and outside actor write authority. Obvious symlinks and nonregular files refuse, but path checks do not establish security against a malicious parent or mount race. This module implements no filesystem watcher, authentication, encryption, durable anti-rollback storage, operating-system sandbox or native asynchronous runtime.

The file ceiling is 4 MiB, with smaller per-source limits. There are at most 256 private keys, 64 KiB per value and 512 KiB total private values, plus 64 KiB per helper context and 512 KiB total context bytes. The existing roster, identifier and 1 MiB complete CommitteeInput limits still apply. Aggregate input size is checked before constructing all helper submissions. The parser temporarily owns hexadecimal text in addition to decoded bytes, and helper inputs copy their selected context. These are logical input bounds, not measured peak memory, latency or syscall counts. Each call rereads and parses the file; it is not constant-time change detection.

## Supervised refresh at the original boundaries

`start_file_review` and `start_file_process_review` build the actual inputs and reference label from a fresh file read, then call the original connected-helper or executable-helper launch. The host still chooses request, round, windows, expected input revision and the complete worker roster. A setup read or input-construction failure withdraws existing input eligibility without fabricating a round or sending a helper packet. Process launch and cleanup ownership remain in the existing driver.

`step_from_file` is a consumer of `step_with_evidence`, a trusted dynamic observation interface inside the SAME SupervisedDriver state machine. It reads after helper I/O, before applying a completed review, and twice along the dispatch path: before authorization and again after reservation before final dispatch. Each dynamic source call is followed by a fresh supplied controller-clock observation. A slow read cannot silently retain the pre-read deadline. The original `step` and `step_with_clock` retain their explicitly fixed-snapshot semantics without extra clock calls or full-input clones; a borrowed-or-owned internal view shares the same execution implementation.

A source error or incomplete observation calls the original inputs_unavailable transition. A successfully observed but changed helper input also withdraws the old approval. The driver does not install new bytes into an already completed review. Restoring old bytes after an observed outage or change cannot resurrect that approval; resumption requires an explicit new review. A permitting review based on earlier bytes is rejected once, while a restrictive review can still apply its frozen evidence with current evidence unavailable.

A failure during the second read can follow a SUCCESSFUL resource reservation. The original permit and reservation remain owned by the job; no refund, new reservation, endpoint call or hidden retry is produced. Explicit cancellation refunds only eligible undispatched rights. Human keys remain subject to their original input revision, scope, epoch, deadline and one-use checks. A subsequent successful dispatch uses the existing exact-policy/witness, source, mediation, activation, identity, fleet, human and endpoint checks, not a separate delivery implementation.

FileDriverStep returns at most two supervisor-only source identities or typed errors alongside the original driver result. The original actor port still receives only its redacted outcome. Error diagnostics never copy file paths, private Snapshot values or other helpers' context. An idle or still-incomplete helper pass need not sample the file because it cannot grant permission. All file I/O is synchronous; bounded bytes do not imply a bounded wall-clock delay on a hostile or failed filesystem.

This is a sampled-observation boundary, not a lock or atomic transaction over the world. A producer can change state after the last read. Strict deployments still require the original endpoint preconditions, trusted capture-currentness/closure contracts and a qualified execution profile. Provider callbacks are privileged and can lie; only the file consumer actually opens and decodes the selected file. Neither route authenticates the producer or proves its declared domain complete.

## File adapter for the mandatory policy-state gate

`PolicyFileSource::attach` installs the existing PolicyStateCapture gate in an unstarted broker and retains its original, noncloneable PolicyStateWriter. It owns the FileEvidenceSource, not a duplicate snapshot ledger. The separately implemented state source and its delivery checks remain unchanged. A new complete file version becomes one ordered full-image StateEvent followed by its closure marker. Subsequent healthy reads of the same parsed file do not append duplicate state records or spend the event quota again.

Every read still opens and validates the actual file. A read error, wrong namespace, false-complete observation or source refusal withdraws the current capture closure. Direct calls through the existing authorization and dispatch APIs then refuse too, even when supplied an old Snapshot with complete=true. Dropping the adapter drops the original writer and disables the live source. Neither its source status nor an earlier returned snapshot can re-create a writer or bypass that gate.

After a nonfatal observation outage, a successful reread records a NEW full-image event and a NEW closure marker, even if the producer restored the exact old file bytes. It does not close an old event prefix to hide the observation gap. The dynamic driver separately invalidates the empirical approval when it observes an outage or changed context; reestablishing a policy snapshot does not silently repair that review. A captured-state quota or invalid state event latches its original source fault; later small files do not replenish or heal it. Source replacement remains the existing explicit fenced governance operation.

This adapter applies BOTH the file limits and the existing policy-state stream limits: 256 keys, 8 KiB per value, 64 KiB per snapshot, at most 1,024 lifetime state events and 8 MiB retained event value bytes, or smaller configured StateLimits. Helper contexts still use the file/input limits and never enter the private policy-state map. The file producer's version and the capture source's incarnation are distinct. Local event sequence counts observed complete images, not every external mutation that could have occurred between file reads. A closure proves only that this declared observed image was admitted by the original reference source, not complete physical-world monitoring.

The sealed EvidenceFile interface lets the SAME start/step methods consume FileEvidenceSource or PolicyFileSource without accepting an external file-reader implementation that returns a silent cache. The older explicitly trusted generic observation callback remains distinct and is not promoted to an authenticated file provider. Using the bound adapter does not automatically launch a watcher or poll in the background; the host must drive reads and use its registered gate correctly.

## Existing obligations do not depend on observation availability

Cancellation, receipt acceptance, endpoint detachment/reconnection and reconciliation remain in the original driver and do not read the evidence file. A publication whose acknowledgment is lost remains charged even after source deletion or helper loss. The filesystem endpoint may later establish definitive nonexecution or return its actual execution receipt under its existing retained identity and fence. Source failure does not decide that external outcome, reopen a stream, rewind the controller or reissue a human key.
