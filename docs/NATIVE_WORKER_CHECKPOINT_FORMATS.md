## Existing consumer and positive capability

The original `NativeEvaluator` cold-start APIs consume explicit ByteLevel
`tokenizer.json` profiles, including declared literal special controls, directly
alongside single or sharded Llama/SafeTensors assets. The original raw profile
and the two named [Unicode-17 profiles](UNICODE_PRETOKENIZATION.md) use the same
bounded startup and original tokenizer engine.
Previously startup accepted only a native tokenizer archive even though the
importer and text evaluator were separately implemented. No conversion program,
intermediate file, second tokenizer or alternate inference engine is required.
This is part of the FA-025 original-token/native-helper integration, not a claim
that a particular trained checkpoint or deployment is qualified.

`NativeTokenizerFormat` explicitly selects `NativeArchive`,
`HuggingFaceRawByteLevel`, `HuggingFaceGpt2Unicode17` or
`HuggingFaceLlama3Unicode17`. The existing four bootstrap entry points retain their
native-archive default and existing request structs. Their new
`*_with_tokenizer_format` counterparts select the parser and otherwise follow
exactly the same preflight, file/reader, model, monitor, sampler and evaluator
path. There is no format sniffing or fallback after a refusal.

The selected parser runs against the independently supplied complete decoder
profile. Native policy admission still requires a nonempty control-only stop
set covering every control. JSON normalization, arbitrary regex, templates and
other unsupported transformations remain errors. The two named grammars require
valid UTF-8, and never insert a prefix space; raw mode retains arbitrary-byte
input. A syntactically valid document with the
right vocabulary cardinality is not proof of training semantics or authenticity.
Every format preserves original prompt bytes and original model token IDs.

For files, the existing 16 MiB tokenizer-asset ceiling, per-file limits, shared
asset budget and real EOF checks apply unchanged. Selecting JSON does not grant
the slice importer's larger 32 MiB allowance to file readers. JSON bytes are
charged as actual asset input, not as an invented native archive size. The index
remains in the sharded auxiliary budget. No weight path is opened before
preflight; no shard reader is touched on a tokenizer refusal. Partial reads and
failed attempts do not replenish either budget.

Tied/independent output-head interpretation still comes from `LlamaConfig` and
passes through the original loaders. All shard labels, tensor directories,
aggregate source limits, normalized-bit comparisons and EOF checks are retained.
Model-dependent monitor validation still follows loading, and startup computes
no tokens or votes. A monitor hold, missing reviewed terminal token, truncation
or exhausted generation budget cannot turn a partial `allow` into a verdict.

## Executable worker manifests

`fa-native-helper` now accepts `fa.native-worker/2`. It is still a private
one-request child, using the inherited full-duplex Unix socket on stdin, not a
listener or actor-facing command. A /1 manifest retains exactly its old field
set, string weight path and native-archive selection. Merely changing the schema
number is not sufficient to opt into /2.

A /2 manifest has the same complete `input`, `decoder`, `policy`, `stream`,
`salt_file`, `lifetime`, `startup` and `files` fields, plus the mandatory root
`tokenizer_format`: `native-archive`, `huggingface-raw-bytelevel`,
`huggingface-gpt2-unicode17` or `huggingface-llama3-unicode17`.
The four auxiliary file paths stay strings. `files.weights` is now exactly one
of these tagged objects (fragments, not complete worker manifests):

```json
{"kind":"single","path":"/operator/checkpoint/weights.safetensors"}
```

```json
{"kind":"sharded","index":"/operator/checkpoint/weights.index.json","shards":{"part-0.safetensors":"/operator/assets/first.bin","part-1.safetensors":"/operator/assets/second.bin"}}
```

Every path must be explicit and absolute. Labels and physical filenames may
differ. The source map is bounded by the original shard-count and label-size
ceilings; the original index parser checks the complete inventory and label
syntax before any weight path opens. Missing, unknown, duplicate, conflicting,
wrongly typed or unsupported fields refuse. A declared sharded checkpoint never
falls back to a nearby single file, and no format is inferred from a filename.

The sharded manifest selects the existing index-aware auxiliary-budget
constructor. `startup.weight_bytes` and `startup.weight_calls` remain ONE shared
allowance for the complete weight set and failures, not a quota per shard.
`startup.asset_bytes` and `startup.asset_calls` include the sharded index reads.
Existing hard file/aggregate limits still apply. No budget is enlarged or reset
in response to a loading error.

The executable attaches the original socket before reading the manifest. Its
one original process lifetime starts after bounded manifest parsing and before
salt, asset and weight loading. Both source branches return the same fresh
native evaluator to the original worker loop, with that same lifetime and step
allowance. Startup does not compute a verdict, issue a permit, bypass a probe,
renew the clock or create a reconnect/retry path. Manifest I/O is bounded by its
existing read/size limits rather than this later lifetime. Filesystem calls and
single numerical steps are still not preempted; the parent's cutoff and process
ownership remain necessary. These APIs are not an OS sandbox or authentication.
